# Obol 0.3.0

This release adds an optional self-hosted central server for remote desktop and iOS clients. Standalone local desktop remains available and does not sync or overwrite its local data.

## Included

- Dedicated `docker-compose.self-hosted.yml` deployment for the Elysia BFF, Nuxt web client, and private PocketBase. PocketBase has no published host port; server configuration requires explicit secrets and a public HTTPS origin.
- Single-owner remote identity with setup-token bootstrap, password login, revocable per-device sessions, cookie transport for hosted web, Bearer transport for desktop/iOS, and a 30-day hard session cap.
- Explicit desktop local/remote selection. Remote server URL and session are stored separately from the local profile; session expiry, endpoint changes, offline errors, and returning to local mode are handled without data transfer.
- Capacitor 8 iOS application that packages the existing Nuxt/Vue UI. Remote sessions use iOS Keychain storage.
- Responsive layouts for narrow screens and safe-area-aware native UI.
- Separate release-candidate workflow. A merged `rc/<version>` pull request with `desktop/app.json` set to `X.Y.Z-rc.N` creates an `rc-<version>` GitHub prerelease. Candidate updater URLs are isolated from stable `release-*`, `latest`, and the Homebrew cask.

## Operator setup

Follow [the self-hosting runbook](../self-hosting.md). Put TLS in front of the BFF and web loopback bindings. For both native remote clients, set:

```dotenv
OBOL_CLIENT_ORIGINS=views://mainview,capacitor://localhost
```

Remove origins for clients the deployment will not serve. Keep an offline PocketBase volume backup before upgrades.

## Scope limits

- One owner per server. Every valid session sees the same deployment data; multi-user sharing and per-record ownership are not included.
- Central hosting is self-managed. Obol does not operate a hosted service.
- No local-to-server import, synchronization, or merge is performed.
- iOS simulator build and launch are verified. App Store signing, provisioning, and submission are not part of the desktop release workflow.
- Candidates are installed manually. Each candidate updater URL remains pinned to its own prerelease; install a newer candidate manually, then use the stable release channel after the final cut.
